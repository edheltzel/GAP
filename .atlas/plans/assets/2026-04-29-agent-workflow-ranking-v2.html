GitHub-Native AI Workflow Stack

Atlas research synthesis · Round 2 · 2026-04-29 · 5 parallel researchers (Perplexity / Gemini / Claude / Grok / Codex)

Round 1 (BMAD/Beads/Backlog.md) · superseded

GitHub Issues + Milestones + Projects v2 IS the spine. The ecosystem ships 80% of what you need. The remaining 20% is a single ~400-LoC Bun CLI that fills six named gaps no off-the-shelf tool addresses.

All five round-2 researchers converged here. Verdict: don't migrate off GitHub — layer existing tools on top, then close the gaps with a small Atlas-native skill.

★ The rule that prevents rot

The plan is narrative. Issues are the state machine. Never reconcile them.

Plan frontmatter stores github_milestone: 42, github_issues: [101,102,103] — written once at creation, never updated manually.

Each issue body contains one line: Plan: .atlas/plans/2026-04-29-slug.md — written once, never updated.

Neither side is ever reconciled against the other. They serve different masters: plans answer "why," issues answer "done/not-done/who."

The 6 Gaps · ~400 LoC Bun CLI

All five researchers agree: GitHub-native + tools above leave six structural gaps. None has an off-the-shelf fix. The gap-filler is one Bun CLI under claudecode/.claude/skills/GitHubOps/cli.ts with subcommands standup, plan-to-issues, set-status.

1Cross-org standup aggregation
No tool aggregates yesterday/today/WIP across multiple GitHub orgs (Alianza, MyChron, Peptideware are separate businesses). gh-standup is single-token; Projects v2 is single-org-bounded.
Fix: atlas standup using gh api graphql with aliased multi-org search queries. ~80 LoC.
2Plan-to-issues with frontmatter writeback
CCPM converts PRDs → issues but doesn't write GitHub IDs back to your .atlas/plans/ frontmatter. Without that, the plan ↔ issues link rots.
Fix: atlas plan-to-issues <path> using gray-matter + Bun $ shell. ~120 LoC.
3Projects v2 status as standup signal
GitHub search API can't filter on Projects v2 custom field values. "Issues where Status=In Progress in Project X" requires enumerating all items via GraphQL and filtering client-side.
Fix: Use label:in-progress as proxy in Search API; fall back to per-project enumerate when needed. ~40 LoC.
4Multi-account aggregation
gh-dash supports multi-org within one account. Multiple GitHub accounts (separate businesses with separate billing) is a hard wall — only the GH_TOKEN env-var trick works.
Fix: ~/.config/atlas/github-accounts.json with {name, token} pairs; iterate per account. ~30 LoC.
5Atlas frontmatter writeback (loop closure)
When milestone closes (all issues resolved), nothing updates the source plan's frontmatter to status: complete or moves it to .atlas/plans/archive/.
Fix: GitHub Action on milestone:closed opens a PR updating frontmatter. ~50 LoC YAML + Bun.
6Milestone freshness/decay signal
GitHub has no API field for "is this milestone still alive?" You need to query all issues, check last activity, infer freshness — 5-10 calls per milestone with no native caching.
Fix: atlas standup computes per-milestone freshness score (last activity, velocity, predicted completion). ~60 LoC.

Code Preview · standup.ts

Sketch from Codex's report — the actual standup query in one GraphQL request: 

const query = `
  query Standup($since: String!) {
    closed: search(query: "is:issue is:closed closed:>=$since assignee:@me", type: ISSUE, first: 30) {
      nodes { ...IssueFields }
    }
    inProgress: search(query: "is:issue is:open assignee:@me label:in-progress", type: ISSUE, first: 30) {
      nodes { ...IssueFields }
    }
    reviewRequested: search(query: "is:pr is:open review-requested:@me", type: ISSUE, first: 15) {
      nodes { ... on PullRequest { title number url repository { nameWithOwner } } }
    }
  }
  fragment IssueFields on Issue {
    title number url closedAt repository { nameWithOwner } milestone { title }
  }
`;

const ghData = await $`gh api graphql -f query=${query} -f since=${since}`.json();
// → feed to Anthropic SDK for one-paragraph summary
// → write to .atlas/handoffs/YYYY-MM-DD-standup.md

★ Pattern across all three

Every "AI agent project tool" launching in 2026 is building its OWN issue tracker.

Maestro (own task system), Paperclip (own Issues), Multica (own kanban) — all three chose to clone GitHub Issues rather than read from them. This is the structural reason none fits the GitHub-as-spine architecture: their entire moat is the parallel tracker.

Building a thin GitHub-native CLI sidesteps this entirely. You stay on the platform you already use, and benefit from every third-party tool that adds GitHub-native automation later.
