## VERDICT: FIX-FIRST — 1 blocker

The engine is **safe in its default (plan) and safe-apply (no-prune) modes** — which are ~95% of use — and the §6 core invariant is **correctly implemented and independently verified**. It is **not a REJECT**. But it **fails its own Phase 2 acceptance criterion** and carries real (gated) data loss on one supported operation, so it is **not a clean MERGE**.

**The single blocker:** plan §7 Phase 2 verify gate requires *"option-rename triggers confirm + **preserves assignments**."* The engine triggers confirm ✅ but does **not** preserve assignments ❌ — a rename is forced through destructive remove+add, resetting every item assignment on that option, and the one safety signal (the "resets N assignments" warning) can silently read **0** when N>0. See F1.

## Decision #3 ruling (report-only vs auto-reassign) — escalation answer for Ed

**My independent ruling: the worker's instinct is RIGHT — reject auto-reassignment — but the implementation is an INCOMPLETE reading of §6 for renames, and that gap is the blocker.**

- **Auto-reassign-by-inference: REJECT.** A name-keyed diff fundamentally cannot distinguish a rename ("In Progress"→"In-Progress") from a genuine remove+add. Any *automatic* reassignment would have to guess the old→new mapping; guessing wrong mis-assigns items — strictly worse than an honest reset. The worker's argument ("auto-reassign would be guessing") is sound engineering judgment. Do not build inference-based reassignment.
- **Report-only as the default: ACCEPT** — for *genuine removals*, reset-to-empty is the correct, expected outcome; there is nothing to preserve.
- **BUT "report-only" is not faithful to §6 for the RENAME case.** §6 says *"re-resolve all affected item field values after the mutation"* and the Phase 2 gate says *"preserves assignments."* The worker read "re-resolve" as "re-snapshot names→IDs into the lockfile" (`Reconcile.ts:410-414`). That is a defensible literal reading, but it does **not** preserve assignments across a rename, and a rename is a first-class supported edit.
- **The correct resolution is NOT auto-reassign — it is an id-preserving in-place rename.** Read-only introspection confirms `ProjectV2SingleSelectFieldOptionInput` accepts an optional `id` alongside the required `name`, so sending `{id: <existing>, name: "<new>"}` renames an option **in place, carrying its assignments** — zero guessing. The engine has no such path today because every rename is decomposed to remove+add by the name-keyed diff. Add an explicit rename signal (e.g. `--rename "Status:Old=New"` or an interview-supplied mapping) that performs the in-place rename; fall back to report-only (with accurate capture, F2) only for true removals.

**Bottom line for Ed:** keep report-only, do **not** add inference-based auto-reassignment, **and** add an explicit id-preserving rename path before relying on prune for renames. Until then, "preserves assignments" (Phase 2 gate) is unmet.

## Findings

### F1 — [BLOCKER] Rename resets item assignments; violates the Phase 2 "preserves assignments" gate, and the warning can read a false 0
**Files:** `reconcile-core.ts:65-75` semantics (rename = delete+create); `Reconcile.ts:345-351` (apply); `Reconcile.ts:175-190, 346-348` (the count).
**Evidence:** A name-keyed diff classifies a rename as a destructive removal of the old option + a safe add of the new (test `reconcile-core.test.ts:65-75` codifies exactly this). On apply under `--prune --confirm`, the old option is dropped from the full-replace union → GitHub resets every item assigned to it; the new option is created empty. No reassignment is attempted (Decision #3 report-only). This directly contradicts plan §7 Phase 2: *"option-rename triggers confirm + preserves assignments."* Compounding it, the sole safety signal — `countAssignments` (`Reconcile.ts:175-190`) — matches the field value by `it[fieldName.toLowerCase()] ?? it[fieldName]` (`:183`); `gh project item-list` JSON does not key custom fields by the lowercased display name (multi-word fields like "In Progress" slugify differently), so a key miss silently yields `0`, printing *"resets 0 item assignment(s)"* for a removal that orphans many. A false 0 is worse than no warning — it actively green-lights the loss.
**Why blocker:** real data loss on a supported op (rename), unmet explicit acceptance criterion, and the mitigating warning is unreliable. (Gated behind `--prune --confirm`, so not silent in the default/safe paths — which is why it's a scoped blocker, not a REJECT.)
**Fix:** add an id-preserving in-place rename path (Decision #3 ruling above); and make `countAssignments` resolve the real item-list key or return `-1`/"unknown" rather than a confident `0`.

### F2 — [should-fix] Destructive removals are not recoverable — the item→option mapping is discarded
**File:** `Reconcile.ts:175-190` (counts only), `:410-414` (post-apply lockfile re-snapshot).
**Evidence:** Before a destructive option removal the engine computes a *count* but never records *which* items held the option. After the full-replace those assignments are gone with no artifact to restore from. §6's "re-resolve affected item field values" is satisfiable cheaply by snapshotting the affected item→option pairs to the lockfile/an artifact before the write.
**Fix:** capture and persist the affected item→option assignments prior to any destructive removal (enables manual recovery; also makes the warning exact).

### F3 — [should-fix] `applyOptionUnion` is not guarded on `s.exists`/`s.fieldId` — relies on the API externally rejecting a wrong-type/undefined write
**File:** `reconcile-core.ts:317-318` + `Reconcile.ts:343-351` (`applyOptionUnion(s.fieldId!, s.union)`).
**Evidence (both sub-reviewers, independently):** Two paths reach the apply loop with `s.exists===false`:
  (a) a field that exists live as **TEXT** while the spec wants SINGLE_SELECT — `diffFields` emits a *warning* but no create op (`core:287-289`), so there's no re-snapshot, and `diffOptions` (called unconditionally at `core:318` on `undefined` options) classifies all desired options as creates → `s.ops` non-empty → apply calls `applyOptionUnion` against the **TEXT field's id**;
  (b) post-create read-after-write lag — if the re-snapshot (`Reconcile.ts:336-340`) doesn't yet see a just-created field, `s.fieldId` is `undefined` and `s.fieldId!` interpolates `fieldId: undefined` into the mutation.
Both are **abort-not-corrupt today** (the GraphQL API rejects options on a TEXT field / a malformed id), so this is should-fix, not blocker — but the engine does not enforce its own invariant; it leans on an external API rejection. The `exists` flag is computed precisely for this and then never read in the apply loop.
**Fix (one guard closes both):** `if (!s.exists || !s.fieldId) throw new Error("field not resolved after create/re-snapshot — re-run")` before `applyOptionUnion`.

### F4 — [should-fix] The entire IO shell (`Reconcile.ts`) is unit-tested **zero** percent — including the destructive gate
**Evidence:** All 19 tests import only from `reconcile-core.ts`. No test exercises `parseArgs`, `applyOptionUnion`, `optionLiteral`/`colorLiteral`, `resolveLockdir`, `countAssignments`, the apply orchestration, or — most importantly — the `--prune`-requires-`--confirm` gate (`Reconcile.ts:321,372`). The gate logic is correct *by reading*, but a future refactor that inverts the boolean or moves the gate after the apply loop would keep all 19 tests green while shipping a board-wiping engine. Root cause: `gh()` is a hard-wired module-level `Bun.spawnSync` (`Reconcile.ts:42-48`), so nothing in the shell is testable without injecting an executor.
**Fix:** make `gh()` injectable (or extract the gate + orchestration into pure, testable units); add tests for: gate throws on `{apply,prune,!confirm}`+destructive before any mutation; `applyOptionUnion`-skipped when `!s.exists`; `optionLiteral` emits `id:` iff id present.

### F5 — [should-fix] Pure-but-untested serialization helpers; live colour cast `as SelectColor` without validation
**Files:** `Reconcile.ts:114-128` (`optionLiteral`/`colorLiteral`), `reconcile-core.ts:216` (cast), `core:378-417` (`formatPlan`).
**Evidence:** `optionLiteral` is the exact point where id-preservation becomes a wire payload — it is pure and trivially testable yet untested (a regression emitting `name` without `id` would silently churn ids and orphan every assignment — the core §6 failure). Separately, a preserved live option's colour is cast `as SelectColor` with no normalization (`core:216`); if GitHub ever returns an unexpected colour token, `colorLiteral`'s `COLORS.has(c)` throws *mid-`.map()`* inside `applyOptionUnion` (`Reconcile.ts:117,133`) → aborts the whole field reconcile (a robustness DoS, not data loss). `formatPlan`'s destructive-suppressed and warnings branches are also untested.
**Fix:** move `optionLiteral`/`colorLiteral` into the pure core and test them; normalize live colours at the snapshot boundary and surface unknowns as a warning, not a hard throw.

### F6 — [should-fix] GraphQL mutations built by string interpolation rather than variables
**File:** `Reconcile.ts:121-139, 134-138`.
**Evidence:** `optionLiteral` interpolates `JSON.stringify`'d strings into the mutation body; the `graphql()` helper supports `-f` variables but the mutation path doesn't use them. **Not injectable** (JSON.stringify correctly escapes quotes/backslashes/newlines; colour is enum-gated) — worst case is a malformed mutation that aborts, not data loss — but variables would be cleaner and remove the asymmetric-trust surface.
**Fix:** pass `singleSelectOptions` as a GraphQL variable.

### Nits
- **N1** Option **display order is not reconciled** (name-keyed diff) — correct for assignment-safety, but board option order drift is silently unfixed. Document it (`core:152-221`).
- **N2** `parseArgs`: `--project foo` → `Number("foo")` = `NaN`, which is `!== undefined` → enters board mode → `resolveProjectId(NaN)` fails downstream (`Reconcile.ts:255,393`). Validate numeric.
- **N3** `specHash` is 32-bit FNV-1a — fine for audit/display, collision-weak if ever load-bearing (`core:359-371`).
- **N4** A custom `--lockdir` outside `.agents/atlas/artifacts` would not be gitignored (default is safe; user's responsibility) (`Reconcile.ts:286`).
- **N5** `tsconfig.json` `"lib":["ESNext","DOM"]` — `DOM` unused by this Node-style code.
- **N6** No audit trail is written for a *partial* (mid-sequence) failure — `main()` catches and exits before the lockfile re-snapshot, so a half-applied board leaves no record (recoverable by re-run, but blind until then).
