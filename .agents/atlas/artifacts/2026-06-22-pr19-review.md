### F5 — [should-fix→nit] Resolved specs share nested object references with module-level constants (latent Phase-2 footgun)
**Files:** `merge.ts:28–36`, `resolve.ts:16`, `archetypes.ts:31` (`PRIORITY`), `archetypes.ts:10` (`CANON_LABELS`).
**Evidence (independently probed + confirmed by code-reviewer):** `resolve(key, [])` runs `reduce` over an empty array and returns the **exact `ARCHETYPES[key]` object** (including its live arrays). Even with overlays, `extend` copies *arrays* but shares *element references* — `PRIORITY` and `CANON_LABELS[i]` are shared across all archetypes. `resolve()` itself is pure (no mutation), so this is **latent, not a current bug** — nothing in this PR mutates a resolved spec. But `resolve.ts`'s header advertises the output as what "the reconcile engine calls," and a reconcile engine is exactly the kind of consumer that mutates specs in place; `spec.fields.push(...)` or `spec.fields[0].options.push(...)` would corrupt the singletons for the whole process.
**Recommendation:** Either document an explicit "resolved specs are immutable — clone before mutating" contract, or have `resolve` return `structuredClone(...)` of the final accumulator (one line, deterministic). Defensible to defer to Phase 2 per Karpathy simplicity, but the asymmetry (`[]` returns the raw singleton; `[x]` returns a half-fresh object) warrants at least a comment now.
