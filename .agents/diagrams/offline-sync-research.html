Offline issue tracking that syncs back

Ed already runs gh-dash for issues and PRs. The unmet need: a local, offline-readable and offline-editable view of GitHub issues that flows back on reconnect — without abandoning GitHub Issues + Projects as the spine.

2026-07-03 · evidence: live round-trips on a throwaway repo · sources: 2026-07-03-offline-sync-tools-research.md · 2026-07-03-backlog-md-research.md

01Verdict
The pick
Adopt gh-issue-sync as the offline issue layer
Its offline story is complete and tested live: read, edit, close, and file new issues with the network hard-cut; one push on reconnect flushed everything, and its three-way merge auto-merged real concurrent edits while catching a true collision with a field-level diff — nothing silently overwritten in either direction. Pair it with a small pm-tools extension for the one dimension neither tool covers: Projects-v2 Status columns.

02Why not Backlog.md

The first research round asked whether the already-installed backlog CLI could be the sync layer. Three grounded findings closed that door (full report: backlog-md-research.md).

Zero GitHub integration
No API code anywhere in the source — grep for octokit / api.github / gh across src/: zero hits. Its “remote” story is git fetch for resolving task state across branches of the same repo.
Upstream said no
Issue #231 asked for exactly this integration. Maintainer: offline-first focus, “it will have to wait.” Closed not_planned.
Single-project by design
One backlog/ dir per repo, no cross-project view. A custom adapter is ~1.5–3k LOC plus a merge-state store — a worse rebuild of gh-issue-sync.

04Day in the life — the plane workflow

How the winner slots into the Themis flow. Every step names its component; the middle phase needs zero network.

Before going offline
online · ~2 min
  1. Pull each active mirror: gh-issue-sync pull --all — issues, dependencies, milestones snapshot to .issues/.gh-issue-sync
  2. Snapshot board 26's Status column to a local sidecar file.pm-tools BoardOffline (until built: gh project item-list > json)
Offline
plane · no network
  1. Read and triage .issues/open/ — plain markdown; Ed, Themis, and herdr workers all just grep it.files
  2. Work the tasks: edit bodies, close <n> finished items, queue audit-trail notes as <n>.comment.md.gh-issue-sync
  3. File new work: new "…" --label … — temp T-IDs, cross-referencable.gh-issue-sync
  4. Record intended board moves (Ready → In Progress → Done) in the board queue file.pm-tools BoardOffline queue
Reconnect
online · ~1 min
  1. push — creates new issues, three-way merges edits, posts queued comments. Push twice if offline issues cross-reference.gh-issue-sync
  2. pull --all — converge the mirror (file renames happen here).gh-issue-sync
  3. Replay queued Status moves through the reconcile engine's GraphQL layer; /Status and /Continue read the live board as today.pm-tools BoardOffline apply
Placement
Mirrors live outside git or under gitignored .agents/atlas/ — the same local-only precedent as plans and handoffs. GH_ISSUE_SYNC_DIR makes the location explicit for skills. The bundled skill/SKILL.md becomes the worker-facing skill with two Themis addenda: the double-push rule, and “never push in the atlas-config mirror without a brief authorizing mutation.”

06BoardOffline.ts — the smallest fix

One new module in skills/pm-tools/Tools/, ~150–250 LOC by analogy with Reconcile.ts, reusing its existing field/option-ID resolution and safety gates. Sketch only — not built.

snapshot
online · read-only
gh project item-list → .issues/.board-26.json: issue# → Status, item-id, option-ids. The offline board read.
queue
offline · file append
Agents and Ed append desired moves to .board-queue.yml — the same queue-file pattern both tools already use. No network required.
apply
online · plan-mode default
Resolve item-id + Status option-id from the snapshot (re-resolving stale ids via the reconcile engine's GraphQL helpers), then gh project item-edit — plan by default, --confirm to execute, inheriting Reconcile.ts's gates.

07Risks & open decisions
  • Bus factor 1, quiet cadence — gh-issue-sync's last commit was 2026-03-31. Mitigate: pin v0.3.0, wrap in our own skill; worst case degrades to plain markdown + gh.
  • One untested cell — project-membership push (add/remove by title) has source-level evidence only; Project 26 was off-limits during testing.
  • Comment threads stay online-only — ghfs's one killer feature. An upstream pull --comments contribution would erase it; the GraphQL plumbing already exists.
  • Two agent gotchas for the skill — double-push for offline cross-references, and files rename on title change: re-glob by issue-number prefix, never cache paths.
  • ghfs trajectory — very active; revisit in ~6 months for hub and comment pulls. Keep its write path away from the audit trail until the conflict asymmetry is fixed upstream.

Evidence & method notes
Both tools installed locally-scoped (Go GOBIN / bun prefix — the npm package is @ghfs/cli, plain ghfs 404s). Throwaway repo seeded with six issues covering labels, milestone, assignee, closed state, comment threads, and a native blocked-by dependency. Offline cells ran under a proxy blackhole for Go; Node ignores proxy env vars, so ghfs's offline run was re-done with a fetch-killing NODE_OPTIONS preload after the first attempt silently hit the network. All write-backs verified via gh issue view. Auth: gh-issue-sync shells out to gh; ghfs speaks octokit with GITHUB_TOKEN. Themis independently spot-checked the decision-driving claims (upstream issue #231 not_planned, zero GH-API grep hits in Backlog.md, gh-issue-sync's bundled skill) before accepting the reports.
